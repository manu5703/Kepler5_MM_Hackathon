# Medusa — Gen UI Prototype Plan

Building the gen-UI loop **on top of** the existing `LearnGraph.jsx` graph prototype,
plus a thin portal that simulates enough of the platform to produce realistic triggers.

**The one thing being tested:** given a concept, a wrong answer, and grounding material,
does Claude pick the right interaction primitive and fill it with parameters that are
schema-valid, grounded, and pedagogically useful? Everything else in this plan exists
only to feed that loop realistic inputs and show its output.

---

## 1. Why LearnGraph is the right base (not a rewrite)

`LearnGraph.jsx` already contains the exact sockets the gen-UI loop plugs into. Three
placeholder strings in `LearningScreen` are literally "AI goes here":

| Line | Placeholder | Becomes |
|---|---|---|
| 315 | "The tutor would teach this concept step-by-step here…" | **Mid-learning trigger** — the "explain differently" path (spec scenario 6) |
| 334 | "The AI tutor evaluates your answer here…" | **Post-answer trigger** — free-text probe answer graded, then a primitive generated for the gap |
| 363 | "The system provides a detailed walkthrough…" | Stretch: interview/research-framed primitive |

Plus `DiagnosticScreen` already collects multiple-choice wrong answers — that's the
**post-quiz trigger** (spec scenarios 1–5), and it's already wired to real distractors.

And `CONCEPTS[]` already carries per-node prose (`covers`, `industry`, `research`,
`interviewQ`, `researchQ`, `assmt`). That is the seed of a grounding corpus — it stands
in for course ingestion / Bedrock KB with zero extra work.

### The integration insight worth building for

The graph gives us something the gen-UI spec doesn't have on its own: **`prereqs` edges.**

When a student fails `trees`, the real gap is often `recursion`. A flat gen-UI system
grounds in the failed concept. Medusa can walk one edge upstream and ground in the
*actual* gap. So the diagnosis step outputs a `likely_prereq_gap` field, and retrieval
pulls source chunks from **that** node. This is the thing that makes this "gen UI on the
graph" rather than gen UI bolted next to a graph — and it's ~15 lines of code because
the edges already exist.

It also gives a demo moment: student gets a `trees` question wrong → system says
"this is actually a recursion gap" → renders a recursion trace stepper → the `recursion`
node on the graph pulses. Nothing else in the space does that.

## 2. Architecture

### Request contract

```
Trigger { conceptId, triggerType, studentAnswer?, chosenOptionIndex?, targetNode }
   │
   ├─ retrieve(conceptId + its prereqs)  ──► SourceChunk[]   (fake KB: filter by concept id)
   │
   ├─ DIAGNOSE   (Sonnet 5, structured output — not a tool call)
   │     { concept_id, misconception_label, key_point_to_teach,
   │       likely_prereq_gap, confidence }
   │
   ├─ GENERATE   (Haiku 4.5, forced tool use across the 3 primitives)
   │     → exactly one tool_use block
   │
   ├─ VALIDATE   (ajv structural + 9 semantic rules + grounding check)
   │     → ok → render   |   fail → log, fall back, never render
   │
   └─ LOG        (JSONL run record: latency, usage, choice, validation, grounding)
```

**Diagnosis uses structured outputs (`output_config.format`), not a tool call.** Two
reasons: it's not an action, it's a typed return value; and it sidesteps any
forced-`tool_choice`-plus-thinking interaction, letting the diagnosis step use adaptive
thinking freely while the generation step runs thinking-off for latency.

### Repo layout

```
index.html
package.json                 vite + express, one repo, two processes
vite.config.js               proxy /api → localhost:8787
server/
  index.js                   express; holds the API key; /api/generate, /api/run-matrix
  anthropic.js               SDK client; callDiagnose(), callGenerate(); Option A + B
  tools.js                   the 3 primitive tool defs (spec §3), strict flag toggleable
  prompts.js                 system prompts for A (single) and B (diagnose / fill)
  corpus.js                  SourceChunk[] keyed by concept id — the fake KB
  retrieve.js                conceptId + prereq walk → chunks
  validate.js                ajv + semantic rules + grounding scorer
  scenarios.js               the 6 hardcoded scenarios
  log.js                     append JSONL to runs/
src/
  portal/LearnGraph.jsx      existing 8 screens, 3 seams replaced with <GenSlot>
  gen/GenSlot.jsx            loading / error / validation-failure / fallback wrapper
  gen/TraceStepper.jsx
  gen/PredictThenReveal.jsx
  gen/StepVisualizer.jsx
  lab/Lab.jsx                scenario runner + model matrix + metrics + raw JSON
runs/*.jsonl                 one line per generation
test-log.md                  generated by `npm run report`
```

### Two views, one build

- **`/` — Portal.** The existing LearnGraph flow, unchanged, with the three seams live.
  This is what gets demoed.
- **`/lab` — Lab.** The 6 hardcoded scenarios, a model/mode selector, "run all",
  side-by-side Haiku vs Sonnet columns, latency + validation + grounding badges, and
  raw JSON. This is the measurement harness from spec §6, and it's where the actual
  research question gets answered.

### Mock mode

`MOCK=1` serves pre-recorded tool calls with no API call. Two jobs: the portal is fully
demoable with no key and zero latency if the network dies mid-pitch, and it doubles as
spec §7's "fall back to a static pre-written example."

## 3. Corrections to the spec (these change the code)

**1. The model IDs in §2 are stale.** `claude-sonnet-4-6` is previous-generation.
Current: **`claude-sonnet-5`** and **`claude-haiku-4-5`** (no date suffix). I'd also add
**`claude-opus-5`** as a third row — not for production, but as a quality ceiling, so
"Haiku is good enough" is a measured claim rather than a hope.

**2. `strict: true` mostly deletes measurement #5.** Setting `strict: true` on a tool
definition (with `additionalProperties: false` + `required`) makes the API guarantee
schema-valid arguments. If we ship strict from day one, "how often does validation fail"
answers itself — near zero — and we learn nothing.

So: **run the measurement matrix with `strict: false`** to get the true raw failure rate,
and **turn strict on for the portal path.** Reported separately in the log.

The corollary is the important part: with strict on, structural failures vanish and the
*only* remaining failure modes are semantic — a `pause_at_step` pointing past the end of
`steps`, a one-step "trace", a `state` array that changes width mid-animation, an
invented citation. Those are exactly the failures that produce a broken or useless
render. **Spec §7's checklist is therefore the real measurement, not the JSON schema.**

**3. No API credentials in this environment.** `ANTHROPIC_API_KEY` is unset and the `ant`
CLI isn't installed, so nothing can call the model until a key is supplied. The build
proceeds either way (mock mode); the measurement runs need `ANTHROPIC_API_KEY` exported
before `npm run matrix`.

**4. Scenario 3 (47 + 38 carrying) is off-graph.** CS 201 has no arithmetic node. I'd
keep it as a **lab-only control** — it's the cleanest possible test of
`element_type: "number_digits"` and it's worth knowing the visualizer works on an easy
case. The portal's own visualizer case comes from scenario 5 (stack vs queue) and a new
scenario 7 (quicksort partition swaps, `element_type: "array_cells"`), both of which are
real graph nodes.

## 4. Validation checklist (spec §7, hardened)

Structural — ajv against the called tool's schema. Then semantic:

1. `pause_at_step` ∈ [0, steps.length); `correct_option_index` ∈ [0, options.length)
2. `steps.length ≥ 2` — and ≥ 3 for trace stepper (a two-step trace isn't a trace)
3. `source_citation` non-empty **and** passes the grounding check below
4. Length caps: title ≤ 120, annotation ≤ 300, code_snippet ≤ 2000, steps ≤ 20, payload ≤ 20 KB
5. **Step visualizer width consistency** — every `steps[i].state.length === initial_state.length`, and every `highlight_indices` entry in range. *Not in §7; will break the renderer the first time it's violated.*
6. **Trace stepper line numbers** — every `line_number` ≤ the line count of `code_snippet`.
7. **`misconception_label` quality** — kebab-case, ≤ 5 tokens, and **not** just the concept name. Rejects the exact degenerate output §4 rule 3 warns about (`"loops"`).
8. **Predict-then-reveal distractors** — options mutually distinct; when a `studentAnswer` was supplied, `reveal_explanation` must reference the wrong option the student actually picked.
9. **Call stack monotonicity** (trace stepper) — depth changes by at most 1 between consecutive steps. Catches hallucinated recursion.

Rules 5–9 are what separate "schema-valid" from "actually renders and actually teaches" —
i.e. spec question #2. On any failure: log, don't render, fall back.

### Grounding check — deterministic, no second model call

Normalize (lowercase, collapse whitespace, strip punctuation), then compare
`source_citation` against each served chunk:

- longest common substring ≥ 40 chars → **exact**
- else Jaccard overlap of content words ≥ 0.5 → **paraphrase**
- else → **unsupported** (fails validation)

Records `best_chunk_id` and `overlap_score`. This turns spec §6's "did it invent
something?" from a vibe into a number we can put in the pitch.

## 5. Measurement

One JSONL record per generation:

```json
{ "ts": "...", "scenario_id": 2, "mode": "B",
  "models": { "diagnose": "claude-sonnet-5", "generate": "claude-haiku-4-5" },
  "strict": false,
  "latency_ms": { "diagnose": 0, "generate": 0, "ttft": 0, "total": 0 },
  "usage": { "input": 0, "output": 0, "cache_read": 0 },
  "chosen_tool": "render_trace_stepper", "expected_tool": "render_trace_stepper",
  "choice_match": true,
  "validation": { "ok": true, "errors": [] },
  "grounding": { "verdict": "exact", "best_chunk_id": "cs201-w3-s04", "overlap_score": 0.82 },
  "raw": { }
}
```

`npm run report` renders `test-log.md`: the §6 table, plus a **primitive-choice confusion
matrix** (expected vs chosen across all runs) — that single table is the strongest
artifact for the "how we validated this" pitch line.

### Matrix to run

5 configs × 7 scenarios × 3 reps = 105 calls. At current pricing that's well under a
dollar; run it as often as the prompt changes.

| Config | Diagnose | Generate | Tests |
|---|---|---|---|
| A-haiku | — | haiku-4-5 | Can the cheap model do the whole job? |
| A-sonnet | — | sonnet-5 | Spec's Option A baseline |
| A-opus | — | opus-5 | Quality ceiling |
| B-sonnet→haiku | sonnet-5 | haiku-4-5 | Spec's Option B — the likely production split |
| B-opus→haiku | opus-5 | haiku-4-5 | Does a better diagnosis rescue Haiku's filling? |

**Prediction worth writing down before running:** primitive *selection* is a judgment
call and will separate the models; parameter *filling*, once handed a good diagnosis,
will not. If that holds, Option B with Sonnet→Haiku is the production answer and the
extra round trip is justified. If A-haiku matches everything, Option A wins on latency
and we drop a call. Either result is a clean finding.

### Latency and caching

Measure TTFT and total separately — a trace stepper with 12 steps is a long output, and
TTFT is what determines whether the UI feels alive. The system prompt, the three tool
definitions and the corpus are all prefix-stable, so put one `cache_control` breakpoint
after them and the per-request trigger last. Verify with `usage.cache_read_input_tokens`
— if it's zero across repeats, something in the prefix is varying.

## 6. Scenario → graph mapping

| # | Concept | Graph node | Trigger | Expected |
|---|---|---|---|---|
| 1 | Recursive base case | `recursion` | `factorial(0)` returns 0 | trace stepper |
| 2 | Array index bounds | `arrays` | `i <= len(arr)` | trace stepper |
| 3 | Addition carrying | *(off-graph, lab control)* | `47 + 38 = 75` | step visualizer |
| 4 | Binary search termination | `bst` | predicts search continues past `low > high` | predict-then-reveal |
| 5 | Stack vs queue ordering | `stacks` | expects FIFO from a stack | **ambiguous — observe** |
| 6 | "Explain differently" | `bst` | no wrong answer, slide only | **any — weak signal** |
| 7 | Quicksort partition swaps | `sorting` | mis-tracks the pivot | step visualizer |

Scenarios 5 and 6 are the interesting ones and shouldn't be "fixed" if Claude's choice
differs from the guess — 5 tests whether the choice is *defensible*, 6 tests the
mid-learning path where there's no error signal at all. Record the choice, judge it,
don't force it.

## 8. Out of scope (spec §9, confirmed)

No forum, tagging, promotion ladder, teacher dashboard, Bedrock Knowledge Bases, auth, or
persistence beyond JSONL. No course ingestion — the corpus is hardcoded. Renderers stay
plain; visual quality is explicitly not what's being tested. The API key never touches
the client bundle, even in a throwaway.

## 9. Risks

| Risk | Mitigation |
|---|---|
| No API key in this environment | Mock mode; build is unblocked, measurement needs a key exported |
| Claude picks trace stepper for everything (it's the most general) | The confusion matrix will show it immediately; fix is in the tool *descriptions*, not the system prompt |
| Grounding check too strict, flags good paraphrases | Three-verdict scale, not pass/fail; tune the 0.5 threshold against the first matrix run |
| Long `steps` arrays blow latency | Cap at 20 in the schema description and in validation; measure TTFT separately |
| Two round trips (Option B) too slow to demo | Measured in P3 before committing; A-haiku is the fallback |
